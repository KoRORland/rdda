# RDDA v0.6 — Scope & Gap Register (Detectability Hardening + Adaptive-Adversary Foundation)

**Status:** draft for planning (2026-07-26)
**Builds on:** `v0.5.0` (security remediation + credibility floor — trust chain signed and
verified, control-channel token in a header, per-IP rate limiting, `SECURITY.md`, enforced
no-logs, off-node backups). v0.5 made the **trust chain** unimpeachable; v0.6 turns to the axis
v0.5 explicitly deferred.
**Source of record:** a third-party **detectability / traffic-analysis review** of the `v0.5.0`
snapshot (`~/Downloads/Telegram Desktop/RDDA-detectability-roadmap.md`). The question it drives:
*does RDDA's default behavior emit a signature that identifies a node as automated proxy
infrastructure, independent of the tunnel's cryptographic soundness?* Every gap below is drawn
from that review and **re-verified against the current tree** before scoping (verification notes
inline). This scope also opens the **adaptive-adversary program** that v0.5 registered and
deferred (`2026-07-14-v0.5-scope.md`, "Deferred to v0.6+").

## Purpose

v0.5 answered "can you trust the binary." v0.6 answers a different question: **once the binary is
running, does every RDDA deployment look like every other one — handing a censor a class
signature for free?**

The review is clear that the *timing* fingerprint the project originally worried about is already
solved (the health beat is jittered in interval, padded in size, and suppresses post-downtime
catch-up bursts — verified), and TLS is partly diversified (per-client uTLS pool). What remains is
**sameness across deployments**: a shared default decoy SNI, the literal project name stamped into
every client config, and identical structural parameters on every node. Characterize one node and
the signature generalizes to the whole fleet. **That is what v0.6 closes.**

v0.6 has one theme with two horizons:

1. **Detectability hardening (ships in full).** Break the fleet-wide monoculture: per-node decoy
   selection, a neutral configurable profile name, per-node structural variance, and — the
   strategically load-bearing piece — an **end-to-end reachability sensor** in the health beat
   that reports whether the exit path actually works, not just whether a unit is `active`.
2. **Adaptive-adversary foundation (designed toward; one primitive landed).** The review's §4 is
   a multi-release architecture (multi-transport as a concurrent balanced pool → multi-RU/multi-EU
   pools with client-side ingress failover and RU-side egress balancing). v0.6 does **not** build
   that. It builds the one backbone piece every later feature depends on — the reachability
   **sensor** (§4.1 calls it "the sensor everything else depends on") — and captures the rest in a
   dedicated design register so near-term choices don't foreclose it.

The single highest-value change is **per-node decoy SNI** (review §2.2, P0): today both
`--client-sni` and `--tunnel-sni` default to the identical shared host, so every operator who
doesn't override ships the same REALITY decoy. Fix the decoy first.

## Priority key

**P0** = fleet-wide class signature — one node's characterization generalizes to all deployments;
**P1** = per-deployment tell or the sensor the adaptive program depends on; **P2** = structural
monoculture (individually fine, collectively a fingerprint); **P3** = hygiene / carried-over debt.
(Adaptive-adversary architecture items keep the review's own §4 numbering `#1`–`#10` and carry a
Horizon, not a P-level.)

## Adaptive-adversary architecture (review §4) — registered, designed-toward, mostly deferred

The review's §4 is the durable answer to a censor that eventually characterizes any static design:
*diversity and motion*, then *redundancy with automated failover*. It is a multi-release push and
must not be bolted onto v0.6. v0.6 lands **one** primitive (the sensor, D-3/Workstream C) and
registers the rest so v0.6's choices stay compatible with it.

**Landed in v0.6 (the foundation primitive):**
- **§4.1 #1 reachability self-detection (partial).** The reachability **sensor** in the health
  beat (D-3). v0.6 builds the sensor; it does **not** build the automated *response* (#2) — a
  detected block alerts, it does not yet auto-rotate or shift transport.

**Deferred to v0.7+ (each needs its own design spec; the review's §4.4 backbone is the throughline):**
- **§4.1 #2 automated local response** — on a detected block, rotate parameters / shift transport
  without a human. Gated on the D-3 sensor landing first.
- **§4.2 #3–#6 multi-transport as a concurrent, balanced pool.** Several live transports at once,
  automated failover, concurrent load-balancing (not sequential failover retrofitted), and
  **push-able transport/parameter changes** over the existing pull channel (the §4.4 *actuator*).
  Design note from the review, adopted: conceive the transport layer as a pool of weighted,
  health-checked paths **from day one** so switching and balancing fall out of one mechanism.
- **§4.3 #7–#10 multi-RU / multi-EU architecture.** Client-side ingress **pool** with automatic
  switching (the single highest-value availability feature for the target audience — one blockable
  IP becomes a rotating self-healing set); RU-side egress **pool** with health-weighted
  load-balancing; a coordinated **control plane** managing *sets* (the §4.4 *pool/membership*
  backbone, a substantial step up from today's single-EU-source-of-truth); and failure-domain /
  jurisdiction awareness in rotation.
- **§4.4 censorship-resistant config/pool distribution** — the bridges-by-email problem for
  *configuration*, not just software (software is already solved: signed releases). Research-grade;
  the precondition for the pools to be updatable *under* censorship.

> **Backbone discipline (review §4.4).** The four shared pieces — reachability **telemetry** (v0.6
> lands this), push-based **control** (actuator), **pool/membership** management, and
> censorship-resistant **distribution** — should each be built once, well, as shared
> infrastructure rather than bolted onto each feature. v0.6 deliberately ships the first and
> designs the reachability payload as a *typed sensor result* so the actuator and pool manager can
> consume it later without a rewrite.

## Proposed v0.6 workstreams

Ordering: A is the headline (the fleet signature); B/C harden the remaining tells while the
render/subscription paths are open; C is load-bearing for the whole roadmap; D clears carried debt.

- **Workstream A — Auto-discovered per-node decoy (D-1).** *The release.* Remove the shared SNI
  default; add `rdda dest discover`, which probes a curated popular/CDN set from the node,
  REALITY-validates each, and auto-picks the nearest validating host (opt-in `--scan-cidr` advanced
  mode); write + surface the pick; `doctor` re-validates and warns. This is the one fix that breaks
  the fleet-wide class signature.
- **Workstream B — De-monoculture the client surface (D-2, D-4).** Configurable neutral profile
  name (default off "RDDA"); per-node structural variance in mux params + rule ordering, bounded by
  end-to-end sing-box validity.
- **Workstream C — Reachability sensor (D-3).** *Load-bearing.* End-to-end through-tunnel
  reachability result in the health beat, as a typed sensor payload, reusing the doctor probe;
  preserve the beat's anti-beacon properties. This is both the P1 detectability fix and the
  foundation for the entire §4 adaptive program.
- **Workstream D — Carried debt (D-5).** Drop the `?token=` query bridge from clients and server;
  header-only control-channel auth.

Out of scope for v0.6 (→ v0.7+): the entire §4 adaptive-adversary build beyond the reachability
sensor — automated response, multi-transport pool, multi-RU/EU pools, push-control actuator,
pool/membership management, censorship-resistant config distribution. Each gets its own design
spec; none is a bolt-on to a detectability release.

## Design notes

### Automatic per-node decoy discovery (Workstream A, D-1)

The node **discovers its own dest** rather than inheriting a shared default or a hash-picked entry
from a static list. Two operator criteria drive it: the dest must be **nearby** (low RTT — so a
censor correlating "how far is this 'website' really" against the node's own latency finds nothing
off) and **plausible as a traffic pattern** (a target that legitimately receives large inbound TLS
volume, so the node funneling many connections to it is unremarkable). A co-tenant box that
normally gets ~zero traffic fails the second criterion — it would be a *stronger* tell than the
shared default — so plausibility is a first-class filter, not an afterthought.

**Candidate source (default): probe a curated popular/CDN set from the node.** The binary ships a
maintained list of popular, CDN-fronted domains. These satisfy plausibility **by construction**
(they are high-volume sites), give "nearby" for free (CDN anycast resolves to an edge near the
node), and universally support the REALITY requirements below. The list is a seed of *candidates*,
not the final dest — each node probes and picks independently, so two nodes in different regions
naturally diverge (the "diverse across nodes" property falls out of real topology rather than a
hash). Document the curation criteria (popular + CDN-fronted + unblocked-in-RU + TLS1.3/h2) so
operators can extend it.

**Validation per candidate (from the node).** REALITY only works if the borrowed handshake is
real, so each candidate must pass, or it is dropped: TLS 1.3 negotiated, X25519 key share, ALPN
offers `h2`, valid CA-signed non-expired cert that chains, and an HTTP/2 request returns a real
`200` (not a redirect or parking page). Measure RTT during the handshake. A candidate that fails
any check never becomes a dest — a bad dest means a broken/detectable REALITY handshake.

**Selection: auto-pick nearest, surfaced, doctor-validated.** Rank the passing candidates by
measured RTT and **auto-pick the nearest** at provision time (fits the "operator-grade laziness"
goal). Write the concrete host into `config.yaml` (so it is **stable** across pulls/re-renders — no
runtime shuffling), **print and log** the choice so it is never silent, and let `doctor`
re-validate it on every run. The operator can override by pinning `--client-sni`/`--tunnel-sni`;
discovery only fills the value when unset. Re-selection is **operator-triggered** (re-run `rdda
dest discover`) or prompted by a `doctor` warning — deliberately *not* automatic/periodic in v0.6,
so the REALITY identity does not churn (a dest that changes on its own is itself odd; damping is the
point). Automated re-select is a v0.7+ item under §4.1 #2, consuming the same validation.

**Advanced mode (opt-in): local-CIDR scan.** For an operator who wants a truly co-located dest and
accepts the tradeoffs, a `--scan-cidr` mode sweeps the node's own datacenter range
(RealiTLScanner-style) for hosts passing the same validation. It maximizes "nearby" (same building)
at the cost of noise (the node behaving like a scanner inside RU) and weaker plausibility (co-tenants
can be low-traffic) — so it is **not** the default, and when used it still applies the plausibility
filter (prefer known-CDN/known-popular hosts among the scan hits).

**`doctor` warning.** `doctor` already reaches the REALITY dest; extend it to **re-validate the
REALITY properties** (TLS 1.3 / h2 / valid cert), not just TCP+TLS reachability, and to warn when
the dest fails validation or looks implausible (unreachable, wrong ASN, self-signed). With the
shared default gone, "left it on the default" is replaced by "your dest stopped validating — re-run
`rdda dest discover`." Warning, not hard fail: an operator may have deliberately pinned a host.

**Caveats.**
- *Discovery is a one-shot outbound burst* of TLS handshakes to popular sites at provision — benign
  and web-shaped, but note it runs from inside RU. The scan mode is the noisier path; keep it opt-in.
- *Curated-list rot:* a listed candidate can become blocked-in-RU or drop TLS1.3/h2 over time;
  per-node validation catches it at discovery, and `doctor` catches it later — the list is a seed,
  correctness is enforced by validation, not by trusting the list.
- *Don't front the same edge as the tunnel:* avoid auto-picking a dest on the exact Cloudflare edge
  the RU→EU hop already fronts, to keep the two hops from sharing a correlatable endpoint.

### Reachability sensor payload (Workstream C, D-3)

**Design it as the sensor, not a bool.** §4.1 names this "the sensor everything else in this
section depends on," and §4.4 makes reachability telemetry one of the four backbone pieces. So the
beat field is a **typed result** — reachable/degraded/blocked plus enough signal (latency,
handshake outcome, RST-injection indicator) for a later automated responder (§4.1 #2) and pool
health-weighting (§4.3) to consume it — not a single boolean that a rewrite would have to widen.

**Reuse, don't reinvent.** The doctor through-tunnel probe (`doctor/probes.go:229`) already fetches
through the tunnel to prove the exit path. Factor it so both `doctor` (operator-invoked) and the
health beat (periodic) share one probe implementation.

**Preserve the anti-beacon properties.** The beat's jittered interval (`RandomizedDelaySec`),
size padding (`randomPad`), and no-catch-up-burst (`Persistent=false`) are the timing fingerprint's
*solved* mitigation (review §2.1) — the new field must not regress them. The probe runs as part of
gathering the beat; its result is padded like the rest of the payload. A blocked/degraded result is
recorded and (v0.6) alertable; automated rotation on it is v0.7+ (§4.1 #2).

### Structural variance (Workstream B, D-4)

Bounded by end-to-end validity: both nodes and the Hiddify client are sing-box, so any per-node
variance in mux protocol/`max_streams` must stay a combination all three negotiate. Vary within a
proven-good range, seeded per-node like D-1; don't invent parameters that break multiplex (the
Signal-3 mitigation the integration harness guards). Keep the change inside what the multihost
integration test still passes.

## Tests

- **Workstream A:** unit-test discovery selection against a fake prober — candidates that fail any
  REALITY check (no TLS 1.3 / no `h2` / bad cert / non-200) are dropped; the nearest (lowest-RTT)
  *passing* candidate wins; all-fail ⇒ clear error, not a silent bad dest. Stability: the picked
  host is written to config and unchanged across re-render/pull. No residual single hard-coded
  default in `cli.go`; an explicit `--client-sni`/`--tunnel-sni` still overrides discovery. `doctor`
  test: a dest that fails REALITY re-validation ⇒ warning; a validating pinned host ⇒ no false
  alarm. Extend `checkdest` fixtures off the old constant. (`--scan-cidr` mode: smoke that the
  plausibility filter is applied to scan hits.)
- **Workstream B:** subscription tests assert the profile title is the configured value and
  defaults to the neutral name (update the `UkREQQ==`/`// profile-title: RDDA` assertions in
  `subscription_test.go` / `server_test.go`). Structural-variance test: rendered configs differ
  per-node yet each stays a valid, mutually-negotiable sing-box config; the multihost integration
  harness still brings the tunnel up and negotiates multiplex (no silent Signal-3 regression).
- **Workstream C:** reachability-sensor unit test — reachable/degraded/blocked map to the typed
  result; a blocked exit yields a "blocked" beat while units are still `active` (the exact
  liveness≠reachability case). Anti-beacon regression: the beat is still padded and the timer still
  jittered with `Persistent=false`. EU-side: the sub server accepts and records the new field.
- **Workstream D:** `subserver` rejects a `?token=`-only request (header now mandatory); `health`/
  `pull` send no query token; constant-time header compare preserved; `doctor` control-channel
  probe still passes header-only. Confirm no supported node path still reads the query first.

## Definition of done (v0.6)

No two default RDDA deployments share a decoy SNI — each node **auto-discovers** its own dest by
probing a curated popular/CDN set, REALITY-validating candidates, and auto-picking the nearest
validating host (stable once written, diverse across nodes by real topology); the single hard-coded
default is gone, the pick is surfaced, and `doctor` re-validates and warns when a dest stops
validating or looks implausible. The client
profile name is operator-configurable and defaults to a neutral value, not the project name. The
health beat reports **end-to-end reachability through the tunnel** as a typed sensor result — a
node whose exit is blocked no longer beacons "healthy" on unit liveness alone — while keeping its
jittered, padded, no-catch-up anti-beacon shape. Structural constants (mux params, rule ordering)
vary per-node within end-to-end-valid bounds, so the per-client uTLS diversity is no longer undone
by a uniform structural fingerprint. The `?token=` control-channel bridge is removed; auth is
header-only. The §4 adaptive-adversary program (automated response, multi-transport pool,
multi-RU/EU pools, push-control, pool/membership, censorship-resistant distribution) is registered
in this spec and carried into dedicated v0.7+ design specs — **not** started here, except the
reachability sensor, which is deliberately shaped as the backbone telemetry every later feature
consumes.
